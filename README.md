# rieltor-cleaner-almaty

Второй микросервис проекта, город **Алматы** (Астана — отдельный такой же
сервис из своего репозитория; общего состояния у них нет). Забирает
`baseline` у `rieltor-collector-almaty`,
размечает объявления через OpenAI (комната вместо квартиры, апарт-отель,
посуточная аренда и т.п.) и отдаёт потребителю **готовый чистый baseline**
— строки объявлений, из которых уже вычеркнут мусор.

Отдельный сервис, не часть коллектора — намеренно: у коллектора внешняя
зависимость krisha.kz, у этого — OpenAI. Сбой одной зависимости не
должен останавливать другую половину системы.

## Архитектура одним взглядом

```
rieltor-collector  --/baseline/table-->  rieltor-cleaner  --/baseline/clean-->  потребитель
   (полные данные)                   (разметка + снимок)       (чистые строки)
```

Чистый baseline **хранится у cleaner** и пересобирается целиком в конце
каждого 12-часового цикла из свежей выгрузки коллектора. В снимок попадает
объявление, только если оно размечено **по текущему тексту** и не
забраковано. Новые и изменённые объявления ждут разметки и появляются в
снимке через один-два цикла (12–24 часа): сначала цикл отправляет их в
OpenAI, а следующий забирает результат. Пропавшие с сайта уходят из снимка
на ближайшей пересборке, цены у опубликованных обновляются там же.

Пустой снимок не публикуется никогда: на холодном старте, пока ИИ ещё не
вернул ни одного вердикта, `/baseline/clean` отдаёт 503 («ещё не собран»),
а не 200 с нулём строк — иначе потребитель принял бы это за «объявлений
нет» и затёр бы свои данные.

Плата за такую схему — цены в выдаче на момент последнего цикла, до 12
часов давности. Зато в «чистом» baseline не бывает неразмеченного мусора,
все страницы из одной выгрузки, и выдача работает, даже когда коллектор
лежит.

## Что решает ИИ

Единственный вопрос: **можно ли использовать объект в базе сравнения цен —
это целая квартира в долгосрочную аренду в обычном для аренды состоянии**.
Ответ бинарный — `usable: true|false`, плюс `reason_code`. Поле `reason` заполняется только для отбракованных; вердикт, где `usable` противоречит `reason_code` (например `true` + `shared`), валидатор отклоняет и объявление повторяется. Чтобы перепрогнать всю базу новым промптом, задайте в Render переменную `CLEANER_RELABEL_GEN` новым значением (1, 2, …): пока идёт перепрогон, потребитель видит прежний чистый baseline, новый заменит его целиком после разметки всех объявлений (~$0.7). Правки промпта проверяются командой `python prompt_check.py` (набор случаев — `prompt_cases.json`).

`usable=false`: комната, подселение, койко-место, общежитие, хостел,
гостиница, апарт-отель, посуточная аренда, а также замаскированные случаи
— «мини-апартаменты как замена гостинице», объявления о продаже под видом
аренды, офисы в разделе квартир — **и квартиры в нестандартном состоянии**:
без отделки/ремонта (`no_renovation`: черновая, предчистовая, «под ремонт») и
без мебели (`unfurnished`) и без основной бытовой техники (`no_appliances`:
нет холодильника, стиральной машины, плиты или кухни); плюс запасное правило
`other_red_flag` — очевидный признак несравнимой цены, не подошедший ни под
один пример. Цена такой квартиры
несравнима с обычной сдачей и портит базу. К объявлениям о продаже под видом
аренды относится и «аренда с выкупом» (платёж 5–15 лет — это покупка, а не
рента), а срок меньше месяца («на две недели») считается `daily_rental`.

`usable=true` получают остальные. Не считаются причиной для отбраковки:
старый или скромный ремонт, дешевизна, мебель «частично», а также пустые
поля ремонта и мебели — «не заполнено» означает «не знаем», а не «плохо».

**Два слоя решают это по-разному.** Структурные поля сайта
(`rent_renovation = без ремонта`, `furniture = без мебели`) ловит бесплатное
правило в `heuristics.py` — точно и без токенов. Случаи, когда об этом
сказано только в тексте, оценивает модель по промпту. Правила прогоняются по
всей выгрузке **каждый цикл**, а не только по новым объявлениям, поэтому
правка правил применяется задним числом сама. Вердикт правила при этом
перебивает ИИ-вердикт.

**Как искать новые красные флаги.** Берём объявления, которые в своём ЖК при
том же числе комнат дешевле медианы по цене за м² на 40% и больше, и читаем
их описания: скидку объясняет либо площадь (у больших квартир цена за м²
ниже, это не флаг), либо реальная причина. Так найдены подселение (в том
числе на казахском), аренда с выкупом, отсутствие техники. Частотный анализ
слов ничего не дал (кроме «подселение»): читать сами объявления надёжнее.

**Ограничение.** Правка `SYSTEM_PROMPT` применяется только к новым и
изменённым объявлениям: у уже размеченных хэш текста не менялся, и повторно
их никто не отправит. Задним числом работает только слой правил.

Оценки мошенничества модель не даёт намеренно — это догадки, которые
она склонна строить на пустом месте (дешёвая квартира ≠ обман).

### Почему модель, а не список регулярок

Проверено на реальной базе: регулярка на слово «комната» даёт сотни
совпадений, из которых почти все ложные («Сдам 1-**комнат**ную квартиру»).
При этом настоящие проблемные объявления регуляркой не ловятся вообще —
например, объявление с заголовком «1-комнатная квартира · 19 м²», где в
описании написано «Мини-апартаменты — бюджетная замена гостинице,
вместимость 1 гость, для приехавших на лечение или в командировку».
Структурные поля говорят «квартира», и только чтение текста показывает,
что это мини-отель.

## API

Все эндпоинты требуют заголовок `X-API-Key` (если задан `CLEANER_API_KEY`).

| Эндпоинт | Назначение |
|---|---|
| `GET /baseline/clean.csv` | **Основной для потребителя.** Весь чистый baseline одним CSV-файлом |
| `GET /baseline/clean` | То же в JSON, постранично (`limit`/`offset`) |
| `GET /verdicts/table` | Сами вердикты без данных объявлений (id, usable, reason_code) |
| `GET /verdicts/review` | Забракованные вместе с текстом — для проверки глазами |
| `GET /verdicts/meta` | Счётчики по категориям + результат последнего цикла |
| `GET /health` | Для healthcheck платформы |

### Забрать файлом: `/baseline/clean.csv`

```bash
curl -H "X-API-Key: $CLEANER_API_KEY" -o clean_baseline.csv \
     https://rieltor-cleaner.onrender.com/baseline/clean.csv
```

Один запрос, весь снимок целиком. Колонки те же, что в `/baseline/table`
коллектора; UTF-8 без BOM; `None` — пустая ячейка, `photo_urls` — как есть.
Заголовки ответа: `X-Built-At` (когда собран снимок), `X-Total-Rows`.
До первой сборки снимка отвечает 503.

### Как потреблять `/baseline/clean` (JSON)

Ответ: `{version, built_at, total, limit, offset, returned, rows}`.
`total` — число строк в снимке, `rows` — объекты в том же формате, что
`/baseline/table` коллектора. `version` — версия выгрузки коллектора, из
которой собран снимок.

```python
rows, offset, built_at = [], 0, None
while True:
    r = requests.get(f"{CLEANER_URL}/baseline/clean",
                     params={"limit": 500, "offset": offset},
                     headers={"X-API-Key": TOKEN}, timeout=60).json()
    if built_at is None:
        built_at = r["built_at"]
    elif r["built_at"] != built_at:      # снимок пересобрали посреди обхода
        rows, offset, built_at = [], 0, None
        continue
    rows.extend(r["rows"])
    offset += 500
    if offset >= r["total"]:
        break
```

`503` означает, что снимок ещё ни разу не собирался (сразу после первого
деплоя). Это не пустая база: локальные данные затирать не надо.

Объявления, которые модель так и не смогла разобрать за `MAX_LLM_ATTEMPTS`
попыток (`usable=null`, `reason_code=llm_failed`), **остаются** в чистом
baseline. Сбой разметки — это «не знаю», а не «плохое»; выкидывать их
значило бы молча терять часть рынка из-за технической ошибки.

## Деплой на Render

`render.yaml` в корне — Blueprint. Dashboard → New → Blueprint → указать репозиторий.

**Почему web service, а не cron job.** Cron job на Render не умеет двух
обязательных здесь вещей:

1. **Нет постоянного диска** («cron jobs can't provision or access a
   persistent disk»). `cleaner.db` стирался бы между запусками, а вместе с
   ним `content_hash` (каждый запуск заново оплачивал бы всю базу) и
   таблица `batches` — то есть отправленные и уже оплаченные batch-задания
   никто бы никогда не забрал.
2. **Нет HTTP** — потребитель не смог бы забрать чистый baseline.

Поэтому расписание живёт внутри процесса (`service.py`), а платформе отдан
обычный web service с диском на 1 ГБ. Стоимость: starter $7/мес + диск
$0.25/мес.

После первого деплоя надо задать вручную: `COLLECTOR_URL`,
`COLLECTOR_API_KEY`, `OPENAI_API_KEY`. Токен `CLEANER_API_KEY` Render
сгенерирует сам — его надо скопировать в сервис-потребитель.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATA_DIR` | `.` | Каталог для `cleaner.db` |
| `COLLECTOR_URL` | — | Базовый URL коллектора (обязательно) |
| `COLLECTOR_API_KEY` | — | Токен коллектора (`X-API-Key`) |
| `OPENAI_API_KEY` | — | Ключ OpenAI (обязательно) |
| `OPENAI_MODEL` | `gpt-5-nano` | Модель. В render.yaml задан `gpt-5-mini` |
| `CLEANER_API_KEY` | пусто | Токен для наших эндпоинтов. Пусто = без авторизации |
| `CLEANER_CYCLE_INTERVAL_H` | `12` | Интервал цикла. Первый цикл — сразу при старте |
| `PORT` | `8002` | Порт HTTP. Render задаёт сам |
| `GROUP_SIZE` | `20` | Объявлений в одном запросе к ИИ. Главный рычаг стоимости |
| `MAX_BATCH_SIZE` | `3000` | Объявлений в одном batch-задании |
| `MAX_BATCHES_PER_CYCLE` | `6` | Заданий за цикл. 3000×6 = вся база за один цикл |
| `MIN_BATCH_SIZE` | `5` | Не отправлять пакет меньше этого — ждать следующего цикла |
| `PILOT_LIMIT` | `0` | Потолок объявлений в ИИ за всё время. **0 = боевой режим** |
| `MAX_LLM_ATTEMPTS` | `3` | Сколько раз переотправлять объявление, на котором ИИ споткнулся |
| `DESCRIPTION_MAX_CHARS` | `600` | Обрезка описания перед отправкой — экономия токенов |
| `CLEANER_STALE_AFTER_S` | `259200` (3 сут.) | Возраст цикла, после которого `/health` отдаёт 503 |

## Стоимость

Замерено на реальном прогоне 1000 объявлений (`gpt-5-mini`, Batch API):

```
input:  229 044 токена  (229 на объявление)
output:  48 919 токенов  (49 на объявление, из них 10 176 — reasoning)
```

Из 229 входных токенов на объявление ~180 — сам текст (в среднем 524
символа при ~2.9 символа на токен), ~49 — доля системного промпта,
размазанная по группе из 20. Без группировки промпт отправлялся бы на
каждое объявление отдельно и съедал бы львиную долю счёта.

Замер на живых объявлениях Алматы (60 штук через синхронный API, тот же
промпт и та же группировка): 248 входных и 64 выходных токена на
объявление. Порядок величины: полный прогон базы Алматы (7.2 тыс.) —
около $0.7, дальше только прирост новых/изменившихся объявлений, то есть
копейки в месяц. Актуальные тарифы сверяйте на странице провайдера.

## Пилотный режим

`PILOT_LIMIT=N` ограничивает **суммарное за всё время** число объявлений,
отданных в ИИ (считает и размеченные, и находящиеся в работе). Нужен,
только если меняли промпт и хотите сначала посмотреть N результатов
глазами:

```bash
curl -H "X-API-Key: <токен>" ".../verdicts/review?limit=50"
```

Эндпоинт отдаёт заголовок, описание и ссылку, сортируя `low confidence`
первыми — там ложные срабатывания вероятнее. Проверять надо одно: не
попали ли в отбраковку нормальные квартиры. Убедились — ставьте
`PILOT_LIMIT=0`.

**Confidence НЕ используется как порог для фильтрации.** Соблазн
«доверять только high» даёт ложноотрицательные: модель ставит `low`
просто из-за краткого описания, хотя в тексте прямо написано «сдаётся
комната». Асимметрия ошибок: комната в базе тянет медианы вниз и портит
оценку **всех** квартир, а ошибочно выброшенная квартира — минус одна
строка из ~7 тыс.

### Разовый локальный backfill интерьера

Контракт будущего обмена фотооценками с mainrieltor, значения статусов и
правила сохранения оценки при пересборке описаны в
[`MAINRIELTOR_INTERIOR_CONTRACT.md`](MAINRIELTOR_INTERIOR_CONTRACT.md).

Фотооценка запускается отдельной командой и не входит в обычный цикл Cleaner.
Сначала сохраните неизменяемый clean baseline в CSV и проверьте план без сети:

```powershell
.venv\Scripts\python.exe backfill_interior_scores.py `
  --input data\almaty_frozen.csv `
  --output data\almaty_enriched.csv `
  --db data\interior.sqlite3 `
  --report data\interior_report.json `
  --concurrency 1 --dry-run
```

Платный smoke-run требует отдельный `RENOVATION_OPENAI_API_KEY` и явный
`--execute`. Начинайте с одного ID; повтор той же команды должен показать
ноль новых API attempts:

```powershell
$env:RENOVATION_OPENAI_API_KEY = "<отдельный ключ>"
.venv\Scripts\python.exe backfill_interior_scores.py `
  --input data\almaty_frozen.csv `
  --output data\almaty_enriched.csv `
  --db data\interior.sqlite3 `
  --report data\interior_report.json `
  --ids 123456789 --concurrency 1 --execute
```

Входной CSV команда не меняет. SQLite фиксирует результат после каждой строки,
а output и JSON-report заменяются атомарно. Полный прогон запускайте только
после проверки smoke-выборки; несколько процессов на одной SQLite-БД не
поддерживаются.

Для первичной подготовки соблюдайте последовательность:

1. Вручную остановить остальные процессы, зафиксировать frozen baseline и
   выполнить первый фото-backfill.
2. Запустить один цикл сбора и очистки, сохранить новый frozen baseline.
3. Снова вручную остановить остальные процессы и выполнить фото-backfill нового
   снимка с той же SQLite-БД.
4. Проверить отчёт и повторный запуск с нулём новых API attempts.
5. При `CLEANER_API_ONLY=1` сначала проверить импорт без записи, затем применить
   его к текущему опубликованному snapshot:

   ```bash
   python import_interior_baseline.py --input /app/data/almaty_enriched_v2.csv
   python import_interior_baseline.py --input /app/data/almaty_enriched_v2.csv --execute
   ```

   Импорт требует полного совпадения количества, ID, порядка строк и набора
   фотографий с текущим `clean_baseline`. При несовпадении он ничего не меняет.
6. Проверить `/baseline/clean.csv`, сохранить резервную копию Cleaner и только
   после этого запускать внешний основной orchestrator.

Collector и основной orchestrator находятся вне этого репозитория, поэтому их
остановка и запуск выполняются отдельно. Backfill сам не запускает другие
процессы.

Для временного запуска на Render установите `CLEANER_API_ONLY=1`: HTTP API,
`/health` и Shell будут доступны, но полный цикл Cleaner и ingest tick не
запустятся. Значение меняют на `0` только после импорта и проверки обогащённого
snapshot. В `render.yaml` первый деплой намеренно зафиксирован в API-only режиме.

Проверить, что коллектор и дифф работают, **не тратя денег на OpenAI**:
временно `MIN_BATCH_SIZE=999999` — цикл дойдёт до отправки и напишет
«объявлений для ИИ меньше порога».

## Что не тестировалось вживую

- Поведение при превышении лимита очереди токенов у OpenAI на полной базе
  (~7 тыс. объявлений одним циклом). Код к этому готов: отправка режется
  на куски по `MAX_BATCH_SIZE`, упавший кусок не блокирует уже
  отправленные и возвращается в очередь следующим циклом — но самого
  отказа на реальном ключе не видели.
- Нет ретраев на уровне HTTP-вызовов к OpenAI: сеть моргнула — исключение
  логируется, задание переносится на следующий цикл.
